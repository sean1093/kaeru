# 0006 — Internationalisation: typed keys, per-feature messages, enforced parity

| | |
|---|---|
| Status | Accepted |
| Date | 2026-10-05 |
| Deciders | Architect (issue #4) |

## Context

Traditional Chinese (Taiwan) and English are **both first-class**: the brief requires full
parity, not a translated afterthought. zh-TW is the primary language of the primary user.

Three forces shape the design:

1. **Nothing may be hard-coded.** A raw string in a component is a bug that reaches a user
   as an untranslated sentence in the middle of a Chinese screen.
2. **Parallel feature branches must not collide.** With one `en.json` and one `zh-TW.json`,
   every feature PR edits the same two files and every rebase is a conflict.
3. **A missing key must be impossible to merge**, not merely visible in review.

Taiwanese terminology matters too (退稅, 收據, 護照, 託運, 海關, 手續費); that is content,
owned by the travel expert, but the architecture must make it easy to review in one place
per feature.

## Decision

### Message bundles are declared per feature and typed

```ts
export const messages = defineMessages({
  'zh-TW': { 'home.nav': '首頁', 'home.title': '…' },
  en:      { 'home.nav': 'Home', 'home.title': '…' },
});
```

`defineMessages<T>` takes `{ 'zh-TW': T; en: { [K in keyof T]: string } }`. TypeScript then
**rejects a missing or extra key in `en` at compile time** — the zh-TW bundle is the shape
of record. The returned bundle is generic over its key union, so `useMessages(bundle)`
returns a `t` whose argument is typed: a typo in a key is a compile error, and renaming a
key is a refactor, not a search.

### Layout

| File | Owner |
|---|---|
| `src/app/messages.ts` | shell strings (brand, navigation label, not-found, update prompt) |
| `src/features/<feature>/messages.ts` | that feature's strings |
| `src/i18n/` | the mechanism only — no product copy |

Key names are namespaced by feature (`home.*`, `settings.*`), and a unit test fails if two
bundles ever claim the same key. A feature PR touches only its own message file.

### Runtime

- `src/i18n/catalogs.ts` collects every bundle with `import.meta.glob('/src/**/messages.ts')`.
  Adding a feature needs no registration.
- The active language is a signal (`activeLocale`). Reading it in a component subscribes
  that component, so switching language re-renders the whole UI with no provider.
- Interpolation is `{name}` placeholders. A value that is not supplied leaves the
  placeholder visible rather than printing `undefined`.
- A missing translation falls back to the key itself — visibly wrong, never blank.
- No plural rules yet. zh-TW has no grammatical plural and the English copy is written to
  avoid the problem; if we need them, `Intl.PluralRules` is in every target browser.

### Detection and persistence

`navigator.languages` is negotiated once: any Traditional Chinese tag → `zh-TW`, `zh-CN` /
`zh-SG` / `zh-Hans*` → *not* zh-TW (fall through to English), `en*` → `en`, otherwise the
default `zh-TW`. The choice is persisted in IndexedDB settings and mirrored to the
`kaeru.locale` boot cache (ADR 0005). `<html lang>` is updated to `zh-Hant-TW` or `en`, which
drives the CJK line-height and letter-spacing rules in the design tokens.

### Formatting

All numbers, currency and dates go through `src/i18n/format.ts`, which wraps `Intl` and
caches formatter instances per locale and options. Yen is formatted with zero fraction
digits — a refund shown as `¥5,000.00` is wrong in a way users notice. Calendar dates are
formatted from a midday-UTC instant so no engine can shift the day.

### Parity is enforced by tests

`src/i18n/catalogs.test.ts` runs over every discovered bundle and asserts: identical key
sets across locales, no empty or whitespace-only values, no duplicate keys across bundles,
and **the same placeholder set in both languages** (so `{days}` cannot be dropped from a
translation).

## Consequences

- A missing translation cannot reach `main`: it fails the type check, or the parity test.
- Feature branches do not conflict over translations.
- Adding a third language (e.g. Japanese) means adding the locale to `LOCALES` and then
  letting the compiler enumerate every bundle that needs the new entry. That is a large but
  entirely mechanical change, which is the right trade.
- Translators work in `.ts` files rather than a translation platform. Acceptable while the
  team writes both languages itself; if that changes, the bundles are plain objects and can
  be exported to any format.
- No runtime i18n library, so no ICU MessageFormat. If a message ever genuinely needs
  gendered or plural selection, that is a new ADR.

## Alternatives considered

- **`i18next` / `formatjs`.** Mature, plural and ICU support, 15–40 KB gzip, and an untyped
  `t('some.key')` by default. We would pay bytes and lose compile-time key checking.
- **One JSON file per locale.** The conflict machine described above, and no key typing.
- **Keys generated from English source text.** Nice for translators, awful for a product
  whose *primary* language is zh-TW.
- **Runtime fetch of translation files.** An extra network request on a device that may be
  offline, for 6 KB of strings that belong in the bundle.
